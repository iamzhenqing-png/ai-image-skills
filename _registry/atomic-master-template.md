# 原子 skill 母版

本文件是「新建一个原子 skill」时的模板与规矩。
本文件**不是 skill**，没有 frontmatter，不会被自动加载，也不参与分发给同事。

阅读方式：
- 第一块【创作约定】= 给建skill 的人看的规矩，**不要**复制进新 skill。
- 第二块【可复制正文】= 整块复制进新 skill 的 `SKILL.md`，然后把所有 `【】` 占位符填掉。

---

# 第一块【创作约定】（不复制进SKILL.md）

## 开工前必做

1. 先打开 `_registry/工作流台账.md` 的**表二**，确认要做的事情**没有**现成原子 skill 能干。
   宁可扩展已有 skill，也不要造第二个功能重叠的。
2. 用官方 `skill-creator` 的初始化脚本直接在独立仓库中建目录，不要手捏：
   ```bash
   python3 "/Applications/CodeBuddy CN.app/Contents/Resources/app/extensions/genie/out/extension/builtin/skill-creator/scripts/init_skill.py" <skill-name> --path "$HOME/dev/ai-image-skills"
   ```
   初始化后运行 `scripts/link.sh`；生成的示例目录里没用到的（`assets/` 等）删掉。上述应用内脚本路径仅适用于当前 macOS CodeBuddy CN 安装位置，版本变化后应先重新查找。

## 命名规则

- 目录名 = frontmatter 里的 `name`，只允许小写字母、数字、连字符（`^[a-z0-9-]+$`）。
- **用功能名，不用步骤名**：叫 `bg-remover`，不叫 `step2-remove-bg`。
  一旦名字里带了步骤序号，这个 skill 就只能给那一条工作流用，复用性直接归零。
- 原子 skill **不加**任何前缀。前缀 `workflow-` 是工作流专用，这样目录里一眼就能分开两类。

## 单一职责判定

一句话说不清它干什么，就该拆成两个。
判断标准：能不能用「输入 X → 输出 Y」一句话说完。说的时候需要「并且」「然后」，就是两个 skill。

## 缺参数时怎么办（必填项缺失时的硬停点）

任何原子 skill 只要有必填参数缺失、为空或明显无效，都必须遵守：

1. **单一来源**：把完整的待填参数清单写成独立文件 `prompts/参数申领单.txt`（或 `references/参数申领单.txt`），
   作为该 skill 唯一的申领单权威版本；`SKILL.md` 里不重复整份内容，只在缺参数协议一节说明「原样输出该文件」。
2. **必填项与选填项分区列出**，必填项标 `❓ 待填写`；选填项若有多个可选值，直接在当前项内用 `/` 列全候选值，
   **不要**在每个候选值后面夹带解释——所有解释性文字统一放到文件最后一段，并标注分隔线，方便用户发送前整段删除。
3. **必填项永远不许有默认值，也不许猜。** 只有选填项可以有默认值（约定为候选列表中的第一个）。
4. 缺参数时，agent 必须用三个反引号的代码块包裹后**一次性原样输出申领单全文**，保留原始换行和空格，
   不得压缩成单段连续文本、逐项追问、删减选项或改写措辞；也不得把申领单里的候选文字当作用户已确认的值去执行。
5. 用户回填后逐项校验；必填项仍缺或明显无效（路径不存在、文件类型不对）时，**立即停止**，
   再次指出缺哪几项，不得编造值继续执行。
6. 全部齐了之后，在真正执行前回显一次完整摘要供用户确认（有 `--dry-run` 能力的 skill 应优先使用它）。

在 `SKILL.md` 的「缺参数时的响应协议」一节里，写清楚触发条件（哪些字段必填）、
引用的申领单文件路径，以及第 4、5 条铁律；不要把申领单正文整段抄进 `SKILL.md`。

## 脚本设计要求

- **单一主入口**：`scripts/<skill-name>.py`，或一个主入口带子命令。不要摆一堆平级脚本让调用方猜该跑哪个。
- **语义化参数**：`--input-dir`、`--output-dir` 这种能看懂的长参数，不用`-a -b -c`。
- **自己定位自己**：脚本内部要用 `Path(__file__).resolve().parent` 找自己的目录，绝不写死 `/Users/xxx/...`。
- **源目录只读**：绝不修改、绝不覆盖输入文件。
- **产物写独立目录**：默认写到输入同级的 `output/`，并支持 `--output-dir` 指定。
- **幂等**：已经处理过的（输出已存在）默认跳过，除非显式加 `--overwrite`。这样中断后能接着跑。
- **单条失败不中断整批**：坏一张图就记一条失败、继续处理下一张，最后汇总「成功 N 张 / 失败 M 张」。
- **不在 skill 目录内产生运行态文件**：缓存、日志、中间产物都不许写进 skill 自己的目录，否则分发时会带上垃圾。
- 需要在 home 下存长期配置（例如 API配置）时，路径写`~/.<skill-name>-profile` 这种形式，不写死绝对路径。
- **平台专属的一键脚本必须标注平台。** 目前团队全是 macOS，允许提供 `.command` 双击脚本，
  但必须在文档里写明「**macOS 专属**」，并同时给出可在终端直接执行的等价命令。
  一键脚本里同样不许写死个人绝对路径——需要默认目录就读环境变量，读不到就要求用户显式提供。

## 写作风格（官方 skill 规范）

- `SKILL.md` 正文用祈使句／动词开头（「运行 xxx」「确认 xxx」），不用「你应该……」。
- frontmatter 的 `description` 用**第三人称**描述，并写清「什么时候该用它」，触发词尽量写全。
- 同一件事只在 `SKILL.md` 或 `references/` 里说一遍，不要两边重复。细节往 `references/` 放，`SKILL.md` 保持精简。

## 建完之后必做

1. **拿 3 个真实样本试跑一遍**，确认输出目录、文件名、跳过逻辑都跟文档写的一致。
2. **刷新台账**：
   ```bash
   python3 _registry/scripts/refresh_registry.py --write
   ```
3. 如果改动了「对外契约」里的任何一条，先查台账表二看哪些工作流会受影响，跟着一起改。

## commit 前缀约定

| 前缀 | 含义 | 要做的事 |
|---|---|---|
| `feat(<skill>):` | 加功能，但对外契约没变 | 直接提交即可 |
| `fix(<skill>):` | 修 bug，对外契约没变 | 直接提交即可 |
| `contract(<skill>)!:` | **对外契约变了** | 必须同时改 `CHANGELOG.md` + 所有受影响的工作流，**三样放进同一次 commit** |

## 「对外契约」为什么必须是7 个字段

工作流层只认这7 个字段，不看你内部怎么实现。少写一个，编排的时候就要靠猜：

| 字段 | 少了会怎样 |
|---|---|
| contract 版本 | 不知道自己适配的是哪一版 |
| 入口命令 | 不知道该跑哪个脚本 |
| 输入 | 不知道参数怎么传 |
| 输出 | 不知道产物在哪，下一步接不上 |
| 硬停点 | 以为能无人值守，结果卡住没人管 |
| 幂等性 | 中断后不敢重跑，怕出重复文件 |
| 依赖 | 环境体检漏项，跑到一半才报缺包 |
